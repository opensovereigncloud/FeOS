# ADR 0015: FeID is the pods' identity SDK

**Status:** Proposed · **Date:** 2026-10-15

## Context

FeTLS (github.com/MalteJ/FeTLS) gives workloads an mTLS identity without
key material in the workload. Its pieces:

- **fetls/1**, the protocol between a workload's TLS stack and a signer
  on the host: versioned NDJSON, negotiated at hello, additive within a
  version. The signer signs only TLS 1.3 CertificateVerify inputs.
- **Libraries** for Go, Rust, Python and TypeScript. They fetch the
  workload's certificate chain and the trust bundle at each handshake,
  delegate the signature, retry, and report each handshake.
- **signerd**, a daemon per node in Go, with an issuer interface, a
  rotation cache and an audit log. It tells workloads apart by peercred
  for containers, by the CID for Kata, by the vsock socket for
  Firecracker.
- A mapping from SPIFFE IDs to subject CNs, which databases map on.
- **fecaas**, a CaaS control plane of CRDs on k3s with Kata, and
  **wired** and **agility**, an eBPF observer of handshakes and an
  application that evaluates the crypto it sees.

FeTLS was built for several runtimes and for a platform that did not
exist yet. An application had to be told where the signer is
(`SECCONT_SOCK`, or `vsock:2:5000` in a microVM), and named its peers by
SPIFFE ID.

FeOS has made the decisions FeTLS left open: pods are microVMs
(ADR 0004), CaaS runs on them without Kubernetes (ADR 0001), the host
side of a pod's identity is `feos-authn` (ADR 0014), and traffic is
recorded without eBPF (ADR 0013). Applications deployed on FeOS are to
use FeTLS's libraries, and that has to work without ceremony.

TLS is the first of the forms an identity takes. Applications will want
tokens too: JWTs for HTTP APIs and the clouds' workload identity
federation, and OAuth and OIDC, with the secrets kept on the host.

## Decision

### FeTLS becomes FeID, and follows FeOS

- FeTLS is renamed **FeID**: TLS is one form of the identity it offers,
  and the tokens to come are others.
- FeID is the SDK with which applications on FeOS use their pod's
  identity: the protocol and the libraries. FeOS is its platform.
- Its host side is `feos-authn` (ADR 0014). signerd goes, and with it
  attribution by peercred and by Kata's CID, and the vsock addresses in
  the libraries.

### Nothing to configure in a pod

- The libraries find the signer at `FEID_SOCK`, else at
  `/run/feos/feid.sock`. Creating a client without configuration works
  in every pod that has an identity. `SECCONT_SOCK` and the paths under
  `/tmp/seccont` go.
- A pod without an identity has no socket. The library fails at start
  and says why: no identity, not a broken platform.
- The application never names its own identity. The pod's spec does
  (ADR 0014).
- The trust bundle is at `/run/feos/ca.pem` as well, for clients without
  FeID, such as `curl --cacert`.

### Peers by name

- A certificate carries the pod's SPIFFE ID as a URI name and, as DNS
  names, the names under which the pod's service is reachable. The
  control plane, which issues it, knows them.
- A client dials a service by its name and checks the server by that
  name, as any TLS client does. Pinning a SPIFFE ID stays an option. A
  server reads the client's SPIFFE ID and authorizes on it.
- A client without FeID checks a server with FeID against the platform
  CA, by name.
- Towards the internet, the libraries trust the WebPKI and the platform
  CA together, as now.

### Development without FeOS

- `feosctl` runs a development signer: feid/1 on a Unix socket, with a
  CA made for the run and an identity named on the command line. The
  same application runs on a laptop and on FeOS.
- The libraries keep their test kits.

### The protocol

- The protocol is fetls/1 as it is, renamed **feid/1**. New operations
  are added to it, as its rules allow; libraries in images built months
  before a node's upgrade keep working with it, and a new library with
  an old node.
- `handshake_report` stays and goes into the pod's events (ADR 0014).
  `wire_event`, which the host's observer sent, goes: ADR 0013 has no
  such observer.
- TLS 1.3 only, Ed25519 only, as now.
- The server side (framing, negotiation, the CertificateVerify check,
  the error codes and the golden frames) is a Rust crate. `feos-authn`
  uses it, and so does the Rust library for its client side. The check
  exists once.
- The mapping from SPIFFE IDs to CNs is the control plane's issuer's.

### In this repository

- FeID moves into FeOS's repository (ADR 0002): the protocol crate
  (`feid-proto`) and the Rust library (`feid`) under `crates/`, the Go,
  Python and TypeScript libraries under a top-level directory for each
  language, the protocol in `docs/architecture/`.
- The libraries are called `feid`. They are published from here to
  crates.io, as a Go module, to PyPI and to npm, and versioned on their
  own, not with FeOS.
- They move without their history. It has no authors beyond test
  identities. The commit names FeTLS's source commit.
- fecaas does not move: CaaS is FeOS's own (ADR 0001). wired does not
  move (ADR 0013). agility stays out; whether it reads the records of
  ADR 0013 and `feos-authn`'s events is decided later.

## Alternatives considered

- **FeID as a repository of its own that FeOS uses.** A change across
  the protocol would be a release on both sides (ADR 0002), and the
  libraries' conformance tests would run against a copy of the signer,
  not against `feos-authn`.
- **FeID gains Kubernetes and SSH.** They share only the pattern with
  it. What makes them work is FeOS's: attribution by the pod's socket,
  the pod's lifecycle, the bindings and the jail. FeTLS would need a
  node model of its own, for runtimes that FeOS does not have.
- **Keeping the name FeTLS.** It is known, but would name only the first
  of the forms.
- **signerd as the host side, or linked into `feos-authn`.** Go does not
  link into a Rust program, and a daemon per node holds every tenant's
  keys (ADR 0014).
- **Peers only by SPIFFE ID**, as now. Every client would have to know
  the IDs of its peers, and clients without FeID could not check a
  server.
- **protobuf or gRPC for feid/1**, like FeOS's APIs. It would put a
  protobuf or HTTP/2 runtime into every application for a handful of
  messages; FeTLS chose NDJSON for that reason.

## Consequences

- An application on FeOS adds a FeID library and creates a client. It
  configures nothing, holds no key, and its database sees its SPIFFE ID.
- The libraries' names and API change: their defaults, and the vsock
  form goes. FeTLS's demo deployments stop working with it, and the
  FeTLS repository is archived once FeID is here.
- The control plane issues certificates with DNS names, so it has to
  know a service's names: that is part of the CaaS API.
- Four libraries are released from this repository. The CI builds and
  tests Go, Python and TypeScript, and runs each library against
  `feos-authn`.
- A peer that cannot do Ed25519 cannot check a FeID server: old Java,
  browsers. Browsers reach services through an ingress with public
  certificates.

## Open questions

- **JWTs.** A `get_jwt(audience)` operation for short-lived JWT-SVIDs,
  with OIDC discovery published by the control plane, would give pods
  HTTP APIs and the clouds' workload identity federation without a cloud
  key in the pod. It puts a bearer token into the pod, if a short-lived
  one bound to its audience.
- **OAuth and OIDC.** A pod as an OAuth client of another service, its
  client secret and refresh token kept by `feos-authn`, which adds the
  access token as the Kubernetes binding adds its credential. A pod's web
  application whose OIDC login the platform runs. Which of these FeID
  offers, and which are bindings of `feos-authn` that need no library.
- ECDSA P-256 for peers without Ed25519. The protocol has a `hash` field
  reserved for it.
- Libraries for Java and .NET.
- agility.
